**2. Amazon SageMaker HyperPod 推理网关：消除 GPU 浪费，首个 token 延迟降低达 82%**
原题：Introducing Amazon SageMaker HyperPod Inference Gateway
分类：推理加速与部署　推荐：⭐⭐⭐⭐（7.5/10）
来源：AWS Machine Learning　发布时间：2026-09-18
入选理由：Kubernetes原生GPU感知推理路由，首token延迟降82%且无需改模型，量化指标明确，部署价值高。

**一句话结论**：AWS 推出 Kubernetes 原生的 GPU 感知路由系统，据基准测试可将首个 token 延迟最高降低 98%，吞吐量最高提升 50%。
**解决的问题**：Kubernetes 默认负载均衡器（轮询、最少连接）不了解 GPU 内部状态，导致请求堆积在繁忙 pod 后面，GPU 利用率不均，首个 token 延迟高达 4 秒以上，需要过度配置，浪费昂贵的 GPU 资源。

**核心技术**
- 两层架构：第一层是每集群网关（EKS 托管 addon），包含 Envoy Gateway、基于请求体的路由器（BBR）和端点选择器（EPP）；第二层是全球推理路由器（GIR，即将推出）。
- EPP 消耗 Prometheus 实时指标（KV 缓存利用率、队列深度、LoRA 适配器驻留、前缀缓存命中率、运行中请求），用加权评分算法选择最佳后端 pod。
- 通过一个声明式 InferenceGatewayConfig 自定义资源定义多模型路由和调度行为，安装简单，无需修改应用代码。
- 与 Kubernetes Gateway API 及 Inference Extension 集成，支持任何 OpenAI 兼容模型服务器，提供优雅降级和自愈机制。

**关键结果**
- 在混合 GPU 代际场景中，Llama-3.1-8B 的 P95/P99 首个 token 时间（TTFT）降低 97%，吞吐量提升 8%；Qwen3-32B 降低 97%-98%，吞吐量提升 50%。
- 在突发流量场景中，Llama-3.1-70B 的 P95/P99 TTFT 降低 94%/98%，吞吐量提升 12%；Qwen3-235B 的 P99 TTFT 降低 89%。
- 在共享提示前缀场景中，Llama-3.1-8B 的 P95/P99 TTFT 降低 26%/43%，吞吐量相当。
- 在均匀舰队、稳定流量下，性能与轮询相当；舰队偏离均匀性越大，收益越大。

**局限与风险**
- 第二层全球推理路由器（GIR）尚未发布，跨集群/跨区域智能路由目前不可用。
- 基准测试仅覆盖了特定模型和实例类型（p5.48xlarge、g5），其他硬件配置下的性能未经验证。
- 在完全均匀的 GPU 舰队和稳定流量条件下，智能路由没有优势，性能与轮询相当。

**适合阅读**：在 Kubernetes 上运行大规模 LLM 推理、希望降低延迟和提升 GPU 利用率的机器学习工程师和平台团队。

**4. 小语言模型能知道自己不知道吗？语义熵作为3B以下模型的置信度信号**
原题：Do small language models know what they don't know?
分类：推理加速与部署　推荐：⭐⭐⭐⭐（8.0/10）
来源：arXiv cs.CL　发布时间：2026-09-21
入选理由：揭示小模型token熵失效，语义熵路由至专家模型提升可达50点，跨家族路由更优，对算力分配有普遍启发。

**一句话结论**：在3B以下的小语言模型中，token级熵近乎为零而失效，但语义熵可有效估计不确定性，用于路由到大模型可提升最高50个百分点的准确率，且跨家族路由增益更高。
**解决的问题**：现有熵方法多针对大语言模型，而小语言模型（<3B）因输出短、过度自信，token级置信度信号失效，导致无法有效判断模型不确定性并优化推理。

**核心技术**
- 评估7种基于熵的置信度方法，包括token熵早停、最大概率早停、概率差早停、token熵路由、语义熵早停和语义熵路由。
- 语义熵估计：生成多个样本，按语义聚类，计算聚类分布熵。
- 阈值校准：使用校准集上正确回答样本的平均熵值。
- 模型级联：当语义熵超过阈值时，路由查询到更大的专家模型。

**关键结果**
- 在35个数据集-模型组合中，91%的token级平均熵接近于零（<0.01 bits），无法区分正确与错误答案。
- 语义熵能恢复有效的不确定性信号，选择性路由可将准确率最高提升50个百分点（如SmolLM 360M到Phi-3.5-mini在ARC-Challenge上）。
- 跨家族路由平均提升22.0%，优于同家族路由的6.8%，表明专家模型的质量比架构兼容性更重要。
- 语义路由在13/35组合中达到最佳准确率，但所有语义方法均消耗更多token。

**局限与风险**
- 所有路由方法均比基线消耗更多计算资源，未实现节省。
- 部分模型（如Gemma3-1B）语义熵接近于零，导致路由信号无法触发。
- 实验仅在消费级Apple Silicon硬件上运行，未测试量化模型。

**适合阅读**：对在资源受限环境下部署小语言模型、关注不确定性量化与模型级联的研究人员和工程师。

**5. RBS-Attention:面向长上下文大语言模型的半径有界稀疏预填充**
原题：RBS-Attention: Radius-Bounded Sparse Prefill for Long-Context Large Language Models
分类：推理加速与部署　推荐：⭐⭐⭐⭐（8.0/10）
来源：arXiv cs.AI　发布时间：2026-09-21
入选理由：免训练双分支稀疏prefill解决均值稀释，128K端到端加速5.97倍且质量近稠密，工程实用性强。

**一句话结论**：RBS-Attention 是一种免训练稀疏预填充方法，通过半径自适应双分支选择减少基线中心导致的误剪裁，在 H100 上对 Qwen3-30B 在 128K 上下文实现最高 5.97 倍 TTFT 加速，同时保持相近准确率。
**解决的问题**：长上下文 LLM 推理中，预填充阶段自注意力计算代价高，稀疏块选择方法常用块关键向量中心代表块重要性，但中心可能掩盖块内少数高相关 token，导致重要块被错误剪裁，称为均值稀释（mean dilution）。

**核心技术**
- 使用居中和最大半径刻画块内离散度，并基于当前提示的半径分布（中位数和90百分位数）计算自适应救援系数 βb，使紧凑块小权重、分散块大权重。
- 双分支评分：基础分支利用中心得分捕获平均相关性，救援分支利用中心得分与半径自适应项的组合识别潜在低估块。
- 对两个分支分别应用相对阈值生成掩码，并与强制保留的 sink、局部窗口和近期块掩码求并集。
- 利用块稀疏 FlashAttention 内核仅对选中的块对执行注意力计算，保持规则的 GPU 执行模式。

**关键结果**
- 在 H100 GPU 上，Qwen3-30B-A3B-Instruct-2507-FP8 在 128K 上下文实现 20.65 倍独立预填充注意力加速、11.92 倍 vLLM 预填充注意力加速和 5.97 倍端到端 TTFT 加速。
- 在 Qwen3-32B 稠密模型上，总体 RULER 准确率为 88.65，稠密注意力达到 89.52；LongBench-v2 上 RBS 达到 0.376，稠密注意力达到 0.394。
- 实验表明，最分散半径五分位数（Q5）中包含 39.5% 的 top-5% 注意力块，远高于均匀分布的 20%。
- RBS-Attention 在相同块选择率下比现有稀疏预填充基线捕获更多 oracle 注意力质量，尤其是在高稀疏区域。

**局限与风险**
- 量化结果基于有限模型和基准，本文未提供更广泛模型规模的验证。
- 半径自适应的启发式依赖于数据特性和超参数选择，可能对不同类型的注意力模式表现不一。
- 仅在 H100 GPU 上报告了系统性能，缺少对其他硬件平台的评估。

**适合阅读**：研究长上下文 LLM 高效推理、注意力稀疏化和 GPU 加速的学者与工程师。

**6. 稠密模型 vs. MoE 模型：活跃参数、吞吐量及选择时机**
原题：Dense vs. MoE Models: Active Parameters, Throughput, and When to Choose Each
分类：推理加速与部署　推荐：⭐⭐⭐⭐（7.5/10）
来源：NVIDIA Technical Blog　发布时间：2026-09-15
入选理由：对比Dense与MoE活跃参数、吞吐及选型，含Nemotron实例，对部署决策有实用指导。

**一句话结论**：MoE 模型通过每 token 仅激活部分参数解耦了内存与计算成本，在吞吐量上优于等总参数量的稠密模型，但部署复杂度和微调挑战更高。
**解决的问题**：如何在稠密模型和 MoE 模型之间做出选择，以优化吞吐量、内存成本和部署复杂度，而不仅仅依据参数总量。

**核心技术**
- 对比稠密模型（每 token 激活全部参数）与 MoE 模型（通过路由器选择少量专家）的架构差异。
- 分析 MoE 路由机制：每层独立路由 token，门控网络选择 top-k 专家，通常包含共享专家。
- 以 Nemotron 3.5 Lightning（30B 总参数，3B 活跃）为例，说明 MoE 结合 Mamba-2 和推测解码的性能优势。
- 从内存预算、并发、微调计划、量化行为四个维度给出部署选择建议。

**关键结果**
- 在相同总参数量下，MoE 模型（如 Nemotron 3.5 Lightning）输出速度远超稠密模型（如 Gemma 4 31B），且成本更低（例如 Lightning 输出速度 235.7-494.2 t/s，价格 $0.22/M vs. Gemma 4 31B 的 36.9-222.4 t/s，$0.40/M）。
- MoE 模型将内存成本（总参数）与计算成本（活跃参数）解耦，VRAM 需加载所有专家，但每 token 计算量仅依赖激活的专家，从而在高吞吐场景下占优。
- 在高并发下，MoE 的延迟优势收窄，但仍保持吞吐量优势；稠密模型在延迟敏感的高并发场景可能更具可预测性。
- 微调 MoE 模型需注意路由器不平衡问题，LoRA/PEFT 或冻结路由器可缓解；量化时对路由器、嵌入层和递归投影层需特殊处理。

**局限与风险**
- MoE 模型需将所有专家加载到 GPU 内存，内存需求与总参数成正比，可能挤占 KV 缓存空间。
- MoE 模型微调更复杂，全量微调可能导致路由器失衡，需采用 LoRA 等参数高效微调方法。
- MoE 模型在量化时，路由器等模块对扰动敏感，需保持较高精度，增加了部署复杂度。

**适合阅读**：需要根据部署约束（内存、并发、微调、量化）选择 LLM 架构的工程团队、MLOps 工程师和推理优化人员。

**1. Claude 将黎曼猜想零点在临界线上的比例下界从 41.6% 提升至 67.2%**
原题：Learning more about Claude's mathematical capabilities
分类：模型能力　推荐：⭐⭐⭐⭐⭐（9.5/10）

**一句话结论**：未发布的 Claude 研究版本通过结合前人工作,将黎曼 zeta 函数零点满足黎曼假设的比例下界从 41.6% 提高到 67.2%,并生成了形式化证明。
**解决的问题**：黎曼假设断言黎曼 zeta 函数所有非平凡零点都位于实部为 1/2 的临界线上,但无法直接证明;一个相关问题是最小化位于该线上的零点比例,此前已知下界为 41.6%。

**核心技术**
- 利用 Aryan 和 Baluyot-Goldston-Suriajaya-Turnage-Butterbaugh 等人去除 Montgomery 技术对黎曼假设依赖的成果,以及 Bombieri 2000 年的工作
- 构造由 Weil 诱导的二次型的函数空间,同时考虑正定子和负定子空间,并利用二次型秩的一阶和二阶矩信息得到不等式
- 在 Claude Code 中运行两次会话,共使用 3100 万输出 token;第二次会话协调约 60 个子代理,运行 2400 条 shell 命令、数百个 Python 脚本,进行数值验证、互审、下载 54 篇 arXiv 论文查重
- 由 Claude 生成 Lean 形式化证明,通过标准验证工具 comparator;由 Anthropic 数学家 Levent Alpöge 和 Ralph Furman 审核,并邀请 Brian Conrey 和 Dan Goldston 审阅

**关键结果**
- 将零点在临界线上的比例下界从 41.6% 提高到 67.2%
- 通过正定和负定子空间统一处理以及允许二次型非对角化,实现了关键技术突破
- Claude 最初尝试 650 个想法均未成功,后在鼓励提示下取得进展;其过程包括子代理分工、数值检查、相互审校和独立复现
- 生成了形式化证明并通过验证,同时产出了论文、非正式说明和详细过程记录

**局限与风险**
- 该结果不能直接证明黎曼假设,所用技术预计不会导致黎曼假设的证明
- 证明依赖于广泛的前人工作,且需要人类专家验证
- 实验使用未发布的 Claude 研究版本,具体模型配置和训练细节未公开

**解决的问题**：部署 2.4T 参数规模的开放权重模型需要数据中心级加速计算，且在长上下文代理式工作负载下面临注意力计算、内存和 KV 缓存增长的约束。

**核心技术**
- 采用全注意力与线性注意力混合架构，线性注意力层用有界循环状态替代增长的 KV 缓存，使计算和内存有界以支持高达 100 万 token 的上下文窗口。

- 利用 GB300 NVL72 的 72-GPU NVLink 域，提供 130 TB/s 的全对全通信，消除专家流量跨传统网络的瓶颈。
- 通过开源推理栈（SGLang、vLLM、NVIDIA Dynamo）和 NVIDIA NIM 提供多种服务路径，无需模型调整即可在 FP8 精度下实现 Day-0 部署。

**关键结果**
- 在 NVIDIA GB300 NVL72 上以 FP8 精度运行，无需额外调优，吞吐量超过每 GPU 4K tokens/s，每用户超过 350 tokens/s。
- 内置推理控制（低/高/超高）可让开发者按请求配置推理深度，在推理质量和计算成本之间进行权衡。
- 通过 NVIDIA NeMo AutoModel 支持对现有检查点直接进行领域特定后训练，无需模型转换，支持完整 SFT 或内存高效的 LoRA 微调。
- 预期后续采用 NVFP4 精度将进一步提升性能。

**局限与风险**
- 当前性能数据仅基于 NVIDIA GB300 NVL72 平台，未提及其他硬件配置或更小规模部署的性能表现。
- 文中未提供与其他模型或推理方案的直接对比，也未给出延迟、成本或功耗等详细指标。
- NVFP4 精度的性能增益尚未实际测量，而是预期未来优化。

**4. 亚马逊 Nova Forge 多轮强化学习自定义奖励函数设计**
原题：Custom reward functions for multi-turn reinforcement learning with Amazon Nova Forge
分类：强化学习　推荐：⭐⭐⭐⭐（7.5/10）
来源：AWS Machine Learning　发布时间：2026-08-14
入选理由：详细讲解多轮RL自定义奖励设计，技术细节丰富，工程实践价值高，但非模型发布级。

**一句话结论**：设计多轮 RL 奖励时需无门控奖励目标行为并显式惩罚失败模式，否则组内方差消失导致学习崩溃。
**解决的问题**：多轮强化学习中，不当的奖励设计会悄然教错行为，甚至奖励组件无学习信号而训练曲线看似健康；如何设计并诊断能支撑多轮代理任务的奖励函数。

**核心技术**
- 将奖励分解为结果奖励、行为奖励和惩罚项，无门控奖励目标行为（如提问后编码）并显式惩罚失败模式（如立即猜测）
- 在 BYOO 环境中安全执行模型生成代码，通过资源限制、临时目录和随机 nonce 防止作弊
- 为每个奖励组件上报指标并跟踪其组内标准差，以识别方差为零的死组件
- 通过 GRPO 组内优势方差面板、按组件排序的转录本和消融测试诊断奖励失效

**关键结果**
- 无门控的提问奖励加立即猜测惩罚使提问率从 34% 提升至 96%
- 正确性评分组件可能因环境绑定错误而返回恒定值，导致其组内方差为零，对梯度无贡献
- 早期版本将提问奖励与正确性门控，并添加效率项，导致策略收敛到单回合猜测，组内方差消失，学习停滞

**局限与风险**
- 示例代码为说明性，部署到生产需额外安全加固
- 奖励组件权重和结构需针对具体任务调整，无法直接泛化
- 诊断依赖事后指标，训练中实时检测并预防崩溃仍具挑战
